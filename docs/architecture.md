# 三层架构

LinkcOS 是 **三层架构 + 一组 Skill 流水**。三层之间有严格的所有权和不变性约定。

```
┌────────────────────────────────────────────────────┐
│  03-schema/    规则层 — 你和 AI 共同演化           │
│  ├─ types.md             类型定义（11 种 wiki 类型）│
│  ├─ templates/           各类型的页面模板           │
│  ├─ CHANGELOG.md         结构演化主索引             │
│  ├─ changelog/           每次迭代的具体记录         │
│  ├─ biweekly-signals.md  日常观察到的演化信号       │
│  └─ proposals/           双周提案（你审批，AI 执行）│
├────────────────────────────────────────────────────┤
│  02-wiki/      知识层 — AI 拥有，你阅读和审阅       │
│  ├─ entities/   人 / 组织 / 产品                   │
│  ├─ projects/   有 KPI 和 deadline 的工作          │
│  ├─ goals/      短期 / 长期目标                    │
│  ├─ concepts/   方法论 / 理论 / 反复出现的思维模式 │
│  ├─ decisions/  已做出的重要决策                   │
│  ├─ journal/    日常随笔（按日期）                 │
│  ├─ build-in-public/  对他人有用的 SOP / playbook  │
│  ├─ reviews/    日 / 周 / 月复盘                   │
│  └─ log.md      所有活动的时间线（append-only）    │
├────────────────────────────────────────────────────┤
│  01-raw/       原文层 — 不可变，AI 只读             │
│  ├─ text/        文字 / 口头输入                   │
│  ├─ external/    外部素材（文章 / 视频 / 截图）    │
│  ├─ screenshots/ 截图                              │
│  └─ voice/       语音原文                          │
└────────────────────────────────────────────────────┘
```

---

## 为什么 `01-raw/` 必须不可变

每个判断都可能错。AI 把一条输入归错了类、漏了关键引用、误解了语境——这都会发生。

**不可变的原文是回滚的根基**。任何时候你都可以：
- 拿原文重新审视一次 AI 的归属判断
- 把过去某段话重新编译成现在新建的某个 concept
- 在系统结构演化后，把旧原文重新跑一遍编译流程

如果原文可以被改、被覆盖、被删，这种回溯就不可靠了。

> 类比：源代码可以被无数次重新编译成不同架构的二进制；二进制不能反推回源代码。

## 为什么 `02-wiki/` 由 AI 拥有

知识管理工具的传统假设是"人是作者，工具是存储"。这种模型下：
- 写入成本高（人要打字 / 排版 / 链接）
- 维护成本更高（一旦笔记多了，没人愿意回去整理）
- 链接断了 / 信息过时了 / 类型混乱了——大多数人 18 个月后就放弃了笔记系统

LinkcOS 反过来：**AI 是 wiki 的主要写作者，你是审阅者和纠正者**。

你只做一件事：输入（语音、文字、截图）。AI 负责编译、关联、提醒、质疑。

这是 LLM 让一切变得可能的核心能力——**写作和归档的成本接近 0**——所以工作流可以重新设计。

---

## 为什么 `03-schema/` 必须共同演化

如果 schema 只能由你定（AI 不参与），系统会僵化——你不会主动想到"应该新增一个类型"。

如果 schema 可以由 AI 自动改（你不参与），你的 wiki 会失控——突然变成 AI 自以为是的样子。

LinkcOS 的折中是 **双周演化提案制**：
1. AI 在日常运行中观察到"演化信号"——比如某种类型的页面反复需要某个字段、某个分类规则反复被你纠正——记到 `biweekly-signals.md`
2. 每两周（由定时任务触发，或你显式调用 `evolve` skill）AI 综合所有信号，生成一份提案：包含 A 类型演化 / B 系统优化 / C 交互方式 三个维度
3. 提案存在 `03-schema/proposals/` 下，每项你在 Obsidian 里手动填 `approved / rejected / deferred`
4. 下次会话启动时 AI 扫描已审批提案并执行

**你不能自动执行任何 schema 修改**——这是合规护栏。

## 6 个 Skill 怎么协作

```
linkc-compile   日常 ingest 主流水（自动触发）
       │
       │  当你说话 / 粘贴 / 截图 → AI 把内容编译到对应 wiki 页
       │
       ↓
   02-wiki/ 各页面
       ↑
       │
ingest          UI/UX 设计参考库（被动查询用）
lint            wiki 健康检查（断链 / 孤儿页 / 过时内容）—— 通常由定时任务周度触发
reflect         日 / 周 / 月复盘 —— 定时任务或显式调用
query           带引用的 wiki 问答 —— 显式调用
evolve          双周 schema 演化提案 —— 定时任务或显式调用
```

每个 Skill 的具体行为见 `.claude/skills/*/SKILL.md`。

## 编译纪律：每条输入的 7 步流水

`linkc-compile` 的核心流水：

1. **保存原文到 `01-raw/`**（不可变）
2. **读索引了解现状**（包括 judgment-corrections.md 吸收过去纠正）
3. **归属判断**（按决策树分到 journal / entity / project / goal / concept / decision）
4. **更新 wiki 页面**（一条输入可能触达 1-10 页）
5. **写 log**（在 `02-wiki/log.md` 追加一行）
6. **回复用户**（用透明化格式：`判断：... / 触达：... / 矛盾：...`）
7. **吸收纠正**（用户纠正归属时，追加到 `judgment-corrections.md`）

完整规则见 `.claude/skills/linkc-compile/SKILL.md`。

## 灵感来源 · Karpathy LLM-Wiki

[Andrej Karpathy 在 X 上提出的 LLM-Wiki 想法](https://x.com/karpathy/status/1729609324302360969)是这套架构的根。LinkcOS 主要的扩展：

- 把 wiki 的"维护权"显式归给 LLM（而不是用户）
- 在 schema 层引入"双周提案制"，让结构能在不失控的前提下演化
- 加入 `journal` 类型，承接所有"不知道归哪儿"的输入，而不是逼用户当下就分类
- 加入 `build-in-public` 类型，区分"对自己有用"和"对他人可复用"两种知识
- 把"三定律"（平等 / 成长 / 诚实）写成系统宪法的最高优先级
